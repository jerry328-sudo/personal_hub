实现目录、各模块文件、函数输入输出及验证结构见 [项目模块与函数设计](./module-design.md)。当前仓库已经落地 Worker 后端、React 页面、D1 迁移、私有 R2 附件流程和本地测试；远程 Cloudflare 资源配置、迁移与生产发布尚未执行。

这一版建议定为：

> **一个 Worker、一个 D1、一个私有 R2 桶；五张业务表、两张认证表和一张附件上传协调表。外部 Agent 判断和去重，平台保存信息、图片、版本和处理状态，提供接口和可配置的 Agent 页面。**

最核心的写入操作只有两种：**创建一个新条目，或者给已有条目追加一个新版本。** 后端不猜测两次提交是不是同一件事，也不自动合并内容。

# 一、项目定位与职责边界

项目可以暂称为 **Personal Hub：个人信息中心**。

它接收个人公开信息监控、AI 定时任务、微信群通知等外部结果，供你统一查看，也供 Agent 在下一轮执行时读取。

| 外部 Agent 负责  | Personal Hub 负责 |
| ------------ | --------------- |
| 搜索、采集、判断相关性  | 按 Agent 保存信息    |
| 理解已有内容、去重    | 返回已有条目的当前内容     |
| 决定创建条目还是更新条目 | 执行明确的创建或追加版本操作  |
| 整理正文、决定重要性   | 展示正文、来源和重要性     |
| 安排下一次运行      | 保存最近一次运行上报      |
| 决定是否需要创建待办   | 保存和展示待办         |

**系统里不放模型、爬虫、微信群读取器或 AI 调度器。** 新增一种监控任务，原则上只需要登记新的 Agent，不需要修改后端业务代码。

# 二、部署结构

## 2.1 只部署一个应用

```text
你的浏览器                  外部 Agent / 脚本
    │                              │
    └──────────────┬───────────────┘
                   │
                   ▼
          Cloudflare Worker
          ┌───────────────────┐
          │ 网页静态资源      │
          │ HTTP API          │
          │ API 使用说明      │
          ├───────────────────┤
          │ Agent 管理模块    │
          │ 条目与版本模块    │
          │ 待办与附件模块    │
          └─────────┬─────────┘
                    │
             ┌──────┴──────┐
             ▼             ▼

后续按需增加：
MCP：另一种工具调用入口

```

Cloudflare Workers 支持将静态资源与 Worker 代码一起部署，因此前端与后端可以使用同一个域名、同一次发布，不必再单独部署 Pages。([Cloudflare Docs][1])

## 2.2 技术选择

建议固定使用 **TypeScript + Hono + React + Vite + D1**。Hono 处理后端路由，React 负责网页，Vite 负责开发与构建；Cloudflare 有对应的部署指南。([Cloudflare Docs][2])

数据库使用 D1 原生接口和参数化 SQL，放在各模块的数据查询文件中。不额外引入数据库映射框架，不搭建微服务，也不引入 KV、队列或工作流引擎。

路由分为两类：页面请求交给静态资源，`/api` 和 `/api/*` 明确交给 Worker。不存在的 API 返回接口错误，不能回退成前端首页。Workers 的静态资源路由支持这种按路径区分的配置。([Cloudflare Docs][1])

# 三、核心模型：Agent、条目、版本、待办

## 3.1 Agent 是稳定的数据分区

一个 Agent 编号对应一项长期监控工作，而不是某次模型会话。Agent 另有 `scope`：普通 Agent 使用 `own`，总管 Agent 使用 `all`；同一时间至多启用一个总管 Agent。

例如：

```text
a001    个人公开信息监控
a002    AI 动态监控
a003    微信群通知
manual  手动记录
manager 总管 Agent
```

以后更换模型、执行平台或者提示词，都可以继续使用原来的编号。名称可以修改，编号保持稳定。

**Agent 编号用于确定数据归属，不是登录密钥。**

总管 Agent 仍然登记在 `agents` 中，因此也有名称、启停状态、最近上报和独立密钥。它不是某一类消息的数据分区：当它代替其他 Agent 创建条目或追加版本时，条目仍属于目标 Agent，同时记录实际操作者是总管 Agent。

## 3.2 条目不限定为“一条公告”

一个条目是一个长期存在的信息对象，可以很小，也可以是一份综合报告。

| 使用方式        | Agent 如何操作         |
| ----------- | ------------------ |
| 一条微信群通知     | 创建一个条目，通常只有一个版本    |
| 某个案件的持续进展   | 保持同一个条目，每次有变化追加版本  |
| 某项监控的完整状态报告 | 保持同一个条目，每次提交完整的新状态 |
| 每日独立简报      | 每天创建一个新条目          |

例如，个人信息监控 Agent 可以只维护一个条目：

```text
条目 17：个人公开信息监控现状

版本 1：首次扫描后的完整结果
版本 2：下一轮扫描后的完整结果
版本 3：加入新发现后的完整结果 ← 当前版本
```

也可以把每份公告分别建成条目。

**采用哪种内容组织方式，由 Agent 的使用约定决定。** 页面另提供 `feed`、`list`、`report` 三种展示方式，仅控制阅读布局，不改变条目、版本或 API 的业务规则。展示方式由你在 Agent 设置中选择，可随时切换。

## 3.3 五张业务表

以下是首版的数据结构，不代表每次 API 都要传输全部字段。

| 表                | 字段                                                                                          | 职责                |
| ---------------- | ------------------------------------------------------------------------------------------- | ----------------- |
| `agents`         | `id`、`name`、`description`、`scope`、`status`、`deleting_at`、`display_mode`、`main_entry_id`、`created_at`、`last_report_at`、`last_result`、`last_note` | Agent 配置、权限、生命周期、页面布局与最近上报 |
| `entries`        | `id`、`agent_id`、`archived`、`read_version`、`completed`、`completed_at`、`created_at` | 条目归属及已读、归档、完成状态 |
| `entry_versions` | `entry_id`、`version`、`created_by_agent_id`、`title`、`content`、`url`、`important`、`created_at` | 各个版本的完整内容与实际操作者 |
| `tasks`          | `id`、`agent_id`、`entry_id`、`title`、`done`、`due_at`、`created_at`                             | 简单待办，可关联来源条目      |
| `attachments` | `id`、`agent_id`、`object_key`、`filename`、`content_type`、`size`、`created_by_agent_id`、`created_at` | 图片归属和 R2 对象元数据，不保存图片二进制 |

其中：

**正文使用 Markdown。** 不要求 Agent 同时提供摘要、结论、正文、行动建议等多份重复内容。来源较多时直接写在正文中，`url` 只是可选的主要来源。

**标题与重要性属于版本内容。** 它们随正文一起记录，查看旧版本时可以看到当时的完整状态。

**版本记录实际操作者。** 普通情况下 `created_by_agent_id` 与条目所属 Agent 相同；总管 Agent 跨 Agent 操作时，条目归属不变，操作者记录为总管 Agent。

**已读、归档、已完成属于条目。** 追加新版本不会覆盖这些个人处理数据。`completed` 默认 `false`；手动完成时记录 `completed_at`，恢复为未完成时清空时间。完成和归档是两个独立动作。

**展示设置属于 Agent。** `display_mode` 默认 `feed`，`main_entry_id` 可为空；指定主报告时必须引用本 Agent 的条目。删除该条目时清空主报告设置，切换布局不删改内容。

**Agent 生命周期必须保存。** `status` 使用 `active`、`disabled`、`removed`、`deleting`，替代单一 `enabled` 字段；删除开始时记录 `deleting_at`，用于跨请求继续清理 R2。移除后可恢复为停用状态，但旧密钥不恢复。`manual` 是不能删除、停用或签发密钥的保留分区；总管身份不能作为消息、待办或图片的归属分区。

**图片属于上传目标 Agent。** R2 保存文件，D1 的 `attachments` 保存归属和对象位置；正文通过稳定的受保护图片 URL 引用，可在多个历史版本中复用同一图片。替换图片须上传新对象，不能覆盖原对象而改变旧版本的显示。

**待办的来源可以为空。** 手动创建的独立待办归入 `manual`；从条目创建的待办继承条目的 Agent 归属。

不设置内容哈希、来源去重键、相似度、请求回执、运行历史或独立审计表。

## 3.4 认证与上传协调基础设施表

认证不改变五张业务表的职责。当前迁移另外创建两张认证表和一张附件上传协调表：

| 表 | 字段 | 职责 |
| --- | --- | --- |
| `agent_keys` | `id`、`agent_id`、`secret_hash`、`created_at`、`expires_at`、`revoked_at`、`last_used_at` | 普通与总管 Agent 的独立密钥，可并存两把以便轮换 |
| `admin_sessions` | `id`、`token_hash`、`created_at`、`expires_at`、`revoked_at` | 网页管理员登录会话 |
| `attachment_upload_leases` | `id`、`agent_id`、`object_key`、`created_at`、`expires_at` | 标记正在进行的附件上传，删除 Agent 时等待有效租约排空，避免遗漏在途对象 |

密钥明文只在签发时返回一次。D1 只保存使用 Worker Secret 作为 pepper 计算的 HMAC-SHA-256；日志不记录密钥、Session 或请求中的认证头。

# 四、版本规则

## 4.1 只追加完整版本，不修改旧版本

条目第一次创建时，同时生成版本 1。

之后每次更新都保存一份完整的新快照：

```text
原状态：v1、v2、v3
追加后：v1、v2、v3、v4
```

**版本号最大的就是当前版本，其余自然是历史版本。**

不维护 `is_current` 标记，不执行“把旧版本改成历史”的额外更新，也不存储正文差异补丁。

新版必须包含完整的标题和正文。可选字段按接口约定处理：没有来源地址就为空，没有指定重要性就使用普通级别，不进行隐式内容合并。

## 4.2 是否追加版本，由 Agent 决定

Agent 判断内容没有变化，就不提交。

Agent 判断需要更新，就调用追加版本接口。

即使两版内容完全相同，后端也不会主动阻止：**平台接受的是调用方明确提出的操作，不负责内容去重。**

## 4.3 只保留一个必要的更新检查

追加版本时，要求带上它刚读取的版本号，例如 `base_version=3`。

只有当前版本仍然是 3，才能追加版本 4。已经有版本 4，就返回冲突，让 Agent 重新读取再决定。

这样可以防止一个较晚完成的旧任务，把过期内容再次写成最新状态。它不需要比较正文，也不需要内容哈希。

实现时，**版本检查和新增必须放在同一次数据库条件写入中**，不能先读取版本、隔一段时间再无条件插入。数据库同时约束同一条目下的版本号不能重复。

## 4.4 历史操作

首版允许查看历史，不允许就地修改历史版本。

需要恢复旧内容时，把旧内容作为一个新版本提交即可。不回拨版本号，不删除后面的版本。

日常移出列表使用归档。永久删除则删除整条记录及其版本，关联待办保留但解除来源关联；不单独删除中间某一版。

永久删除后，平台不保留防止再次收录的去重记录。后续是否重新收录，仍由 Agent 判断。

# 五、Agent API：自身份接口与总管接口

实际业务接口统一放在 `/api/v1` 下。

## 5.1 Agent 常用接口

普通 Agent 使用自身份接口，路径中不再携带可篡改的 Agent 编号。Worker 根据 Bearer Key 得到可信的 `agent_id`。

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/agent` | 读取自身说明、启用状态和最近上报 |
| `GET /api/v1/agent/entries` | 读取自身所有条目的当前版本 |
| `POST /api/v1/agent/entries` | 创建属于自身的新条目及版本 1 |
| `GET /api/v1/agent/entries/{id}` | 读取自身的一个条目 |
| `POST /api/v1/agent/entries/{id}/versions` | 为自身条目追加完整新版本 |
| `GET /api/v1/agent/entries/{id}/versions` | 读取历史版本目录 |
| `GET /api/v1/agent/entries/{id}/versions/{version}` | 读取指定历史版本 |
| `POST /api/v1/agent/report` | 上报本轮执行结果 |
| `POST /api/v1/agent/attachments` | 上传图片，归属由当前密钥确定 |
| `GET / POST /api/v1/agent/tasks` | 读取或创建自身待办 |
| `PATCH / DELETE /api/v1/agent/tasks/{id}` | 修改或删除自身待办 |

新建条目只要求 **`title`、`content`**；追加版本再多一个 **`base_version`**。来源地址和重要性可选。

编号、版本号和系统时间由服务器生成。成功写入后，只返回条目编号与版本号，不把整篇正文再回传一遍。

接口不提供“自动判断新增还是更新”的通用写入操作，避免隐藏行为。

## 5.2 总管 Agent API

总管 Agent 使用独立 Bearer Key 和 `/api/v1/manager` 接口，可以跨 Agent 管理消息：

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/manager/agents` | 读取所有 Agent 的基本状态，不返回密钥信息 |
| `GET /api/v1/manager/entries` | 跨 Agent 查询当前消息，支持 `agent_id`、重要性、完成/归档状态、搜索和游标筛选 |
| `GET /api/v1/manager/entries/{id}` | 读取任意条目的当前完整内容 |
| `GET /api/v1/manager/entries/{id}/versions` | 读取任意条目的历史目录 |
| `GET /api/v1/manager/entries/{id}/versions/{version}` | 读取指定历史版本 |
| `POST /api/v1/manager/agents/{agent_id}/entries` | 代目标 Agent 创建条目和版本 1 |
| `POST /api/v1/manager/entries/{id}/versions` | 为任意条目追加完整版本 |
| `GET / POST /api/v1/manager/tasks` | 跨 Agent 读取或创建待办 |
| `PATCH /api/v1/manager/tasks/{id}` | 修改任意来源的待办 |
| `POST /api/v1/manager/report` | 上报总管 Agent 本轮执行结果 |
| `POST /api/v1/manager/agents/{agent_id}/attachments` | 为目标 Agent 上传图片 |

总管 Agent 管理消息内容、图片和由消息产生的待办，但不能创建、停用或删除 Agent，不能签发或撤销密钥，不能管理管理员会话，也不能永久删除条目。已读、归档、已完成和永久删除属于你的个人处理状态，由网页管理接口负责；普通及总管 Agent 均可读取完成状态，不能通过追加版本清除它。

总管创建或更新内容时，服务端根据目标条目确定 `entries.agent_id`，并把 `entry_versions.created_by_agent_id` 写成总管 Agent 编号。总管不能把已有条目改归属到另一个 Agent。

首版只允许一个启用的 `scope=all` Agent。普通 Agent 的密钥即使修改路径，也不能调用 `/manager`；总管密钥可以调用 `/manager`，但不能调用管理员接口。

## 5.3 管理与网页接口

另外提供 Agent 登记与修改、跨 Agent 信息列表、条目处理状态修改和永久删除接口。

其中，修改条目的已读、归档或完成状态走独立的状态接口 `PATCH /api/v1/admin/entries/{id}/state`；完成操作只需 `{ "completed": true }`，恢复使用 `false`，时间由服务端生成。**修改正文仍然走追加版本接口。** 附件上传使用 `POST /api/v1/admin/agents/{agent_id}/attachments`。

网页与 Agent 使用同一套条目操作，不另写一份“网页编辑逻辑”。

## 5.4 完整读取与分页

`GET /api/v1/agent/entries` 默认返回：

> **该 Agent 已有条目的当前完整内容，包括已完成和归档条目，并附带 `completed`、`completed_at`、`archived`、版本号及图片引用；不包含图片二进制或所有旧版本正文。**

已完成和归档条目仍然返回，是为了让 Agent 知道这些内容已经存在且是否已处理。可显式使用 `completion=all|open|done` 筛选，默认 `all`。网页为了集中处理未完成内容可以请求 `open`，不能将这个网页默认值套用到 Agent API。

列表不能默认只给标题，也不能只返回最近若干条而不说明。数据超过一页时，返回明确的 `next_cursor`；Agent 持续读取，直到游标为空。

分页按稳定的条目编号进行。外部执行器应让同一 Agent 串行执行一轮“读完全部页面—比较—写入”，不为首版增加复杂的跨页快照协议；同时修改某一条目的情况，由版本检查处理。

网页需要轻量列表时，可以显式使用 `view=brief`，只取标题、版本、重要性和处理状态。**精简视图是额外选择，不能替代 Agent 需要的完整内容。**

总管跨 Agent 使用 `GET /api/v1/manager/entries` 时默认返回 `brief`，同样默认包含已完成和归档条目，每行必须包含完成状态。它需要判断某个 Agent 的全部现状时，显式指定 `agent_id` 和 `view=full`，并按游标读取完整内容；单条正文通过详情接口取得。不得仅根据精简标题判断两条内容是否重复。

## 5.5 不另造一套压缩协议

首版使用正常的精简 JSON，正文放在 Markdown 字符串中。

主要节省方式是：不返回无关 Agent、不重复正文、不附带空字段、不默认返回所有旧版本。

不把字段全部缩成单字母，也不使用需要额外记忆列顺序的位置数组。

# 六、API 自动发现

首版只需要两个文档入口。

### `GET /api`

返回一份短的使用说明，内容包括：

**系统用途、接口版本、当前凭据角色、可用接口、如何读取数据、如何新建条目、如何追加版本、分页规则，以及完整文档地址。**

其中必须明确写出：

> 先读取本 Agent 的已有内容，包括已完成和归档内容，读完全部分页后由调用方去重。已完成的同一件事没有新事实时不再创建条目、追加相同内容或重复生成待办；确有新进展时追加原条目的版本，保留完成状态。新的独立事项才创建新条目。平台不执行语义去重，完成状态也不是自动去重保证。

这份说明使用项目维护的固定文本，不从上传正文中生成。

说明内容按凭据角色返回。普通 Agent 只看到自身份接口；总管 Agent 看到总管接口及跨 Agent 读取规则；管理员网页看到管理接口。普通 Agent 的说明中不能出现可调用的跨 Agent 操作。

### `GET /api/docs`

返回完整参数、返回结构、错误约定和少量调用示例。

文档与接口一起进入版本管理，集成测试检查入口鉴权和角色范围；完整调用示例在 staging smoke checks 中复核。首版不必再同时维护多种说明格式和动态工具目录。

MCP 留到需要接入的客户端明确支持并需要它时再加。它只包装现有业务操作，不增加第二套业务规则。

**自动发现解决的是“如何调用”，外部 Agent 的执行环境仍需具备 HTTP 请求能力。**

# 七、监控运行与网页行为

## 7.1 每轮执行只有一个简单约定

```text
读取 Agent 状态
       ↓
读取自己已有的当前内容
       ↓
在外部完成搜索、比较、去重
       ↓
创建新条目，或追加已有条目的版本
       ↓
上报本轮成功或失败
```

同一轮没有新信息时，只需要上报成功，不必创建一条“今天没有变化”的信息。

运行上报只覆盖 `agents` 中的最近时间、结果和简短说明，不建立运行实例、运行历史或检查点系统。

网页显示“最近上报成功”“最近上报失败”或“尚未上报”，不把“数据库能访问”误当成“外部监控一直正常”。

停用 Agent 表示平台停止接受它的内容写入；外部调度器读取到停用状态后应停止执行。平台本身不控制外部 Schedule。

## 7.2 网页保留四个主要页面

| 页面           | 首版内容                                 |
| ------------ | ------------------------------------ |
| **信息收件箱** | 所有 Agent 的当前条目，按来源、重要性、未读、归档、完成状态筛选 |
| **条目详情** | 正文和图片、来源、历史版本、完成或恢复、归档、创建待办 |
| **Agent 管理** | 名称、说明、展示布局、主报告、普通或总管权限、启停、最近上报、密钥轮换与接入信息 |
| **待办**       | 未完成与已完成事项，可选截止日期与来源链接                |

首页以信息列表为主，不做复杂统计仪表盘。历史版本通过选择器查看，不要求首版实现逐字差异对比。

每个 Agent 页面根据 `display_mode` 展示，保留同一套侧栏、正文样式和权限规则：

| 展示方式 | 页面结构 | 适用内容 |
| --- | --- | --- |
| `feed` 信息流 | 日期分组的列表和阅读区，手机逐层进入 | 微信通知、每日动态 |
| `list` 清单 | 单个宽内容区，一条一行，点击原位展开正文和图片；直接勾选完成，不按日期分组 | 待关注事项、文献线索、监控对象清单 |
| `report` 报告 | 单个宽阅读区，默认显示主报告；顶部选择其他条目或历史版本，不常驻条目侧栏、不按日期分组 | 持续维护的一份监控报告 |

清单按稳定的条目创建顺序展示，完成状态通过“全部／未完成／已完成”筛选，不因一次更新时间改变分组。报告优先展示 `main_entry_id`；未设置时默认第一条未归档条目，选择器保留包括已完成在内的其他报告入口。空 Agent 显示接入说明，不生成空报告。布局配置与外部 Agent 怎样组织内容相互独立。

全局收件箱继续按更新时间展示。日期在清单、报告中仅作为辅助元信息；通知截图、图表等可直接显示在正文中，并支持点击放大。

## 7.3 已读状态使用版本号

`read_version` 表示你读到了哪一版。

例如已读版本为 3，当前出现版本 4，网页就显示“有更新”。标记已读时提交实际打开的版本号，而不是直接把后台最新版本全部标为已读。

这只需要条目上的一个字段，不需要独立已读记录表。

归档状态不会因为 Agent 更新而自动取消。内容修改也不会自动创建待办、完成待办或重置待办状态。

## 7.4 条目的已完成状态

“已完成”表示你已经处理了这条动态。它不是 Agent 本轮执行成功、不是已读，也不是待办的完成状态。可以直接把一条动态标为已完成，无需先创建待办。

在清单中勾选完成，或在信息流、报告的正文工具栏点击“标为已完成”；也可以恢复为未完成。完成只修改条目状态，不生成内容版本、不删除正文图片、不自动归档，也不批量完成关联待办。

追加新版后保留完成状态；如果新版尚未读过，则同时显示“已完成 · 有更新”。由你决定是否恢复处理，普通及总管 Agent 不自动重开或隐藏新进展。版本读取、列表与详情都返回同一份条目完成状态。

若清单只是一个 Markdown 正文中的项目列表，首版完成按钮针对整条条目；需要逐项完成的事项应各自建立条目。首版不解析正文中的复选框，也不增加子任务层级。

## 7.5 待办保持简单

待办只有标题、完成状态、可选截止日期和可选来源。

从条目“转为待办”只是创建一条带来源关联的任务。来源以后更新，任务本身保持不变。

首版不做多层项目、复杂重复规则、依赖关系或协作功能。

## 7.6 私有 R2 图片与正文展示

首版纳入一个私有 R2 桶，通过 Worker 的 R2 Binding 读写；不把 R2 管理凭据交给 Agent。Worker 可通过绑定上传、获取和删除对象，桶的公开访问需另行显式开启，本项目保持关闭。([Cloudflare R2 Workers][9]、[R2 公开访问][10])

文件字节写入 R2，正文、完成状态和附件元数据留在 D1。首版上传 PNG、JPEG、WebP 或 GIF，应用限制单张 10 MiB（本项目限制，不是 R2 上限），验证实际文件类型，不接受脚本、HTML 或 SVG 上传。文件名仅作显示，对象键由服务端生成，不允许覆盖已有对象。

上传与引用流程：

1. 使用所属角色的附件上传接口，以 `multipart/form-data` 提交图片。
2. Worker 认证并检查归属，生成附件编号和唯一对象键，写入 R2，再写入 D1 元数据；成功后返回 `{id, url, filename, content_type, size}`。
3. Agent 在 Markdown 正文里引用 `![通知截图](/api/v1/media/{attachment_id})`，然后创建条目或追加完整版本。
4. 保存正文时，Worker 验证本站图片引用存在且属于条目所在 Agent。总管代写时仍以目标 Agent 为归属，不能把其他来源的私有图片任意混入。
5. 网页以同源 `<img>` 加载媒体 URL，浏览器自动附带管理员 HttpOnly Session Cookie；Worker 校验后从私有 R2 返回图片。外部 Agent 下载同一 URL 时带 Bearer Key，普通 Agent 仅可读自己的图片，总管和管理员可读全部。

`GET /api/v1/media/{id}` 是允许三类身份的只读媒体入口，先鉴权和归属检查再读取对象；不能因为 URL 可猜到就放行。返回真实 `Content-Type`、`X-Content-Type-Options: nosniff` 和 `Cache-Control: private, no-store`。密钥不放进图片 URL，正式正文只渲染本站附件图片；外部图片先由执行器上传，Worker 不自动抓取外部 URL。首版不配置公开桶、公开图片域名、图片转换或额外 CDN 缓存。

图片加载失败时显示文件名和“图片暂不可用”，保留正文其他部分。已完成或归档不影响图片读取，切换历史版本显示原有图片。附件在 Agent 内独立保存；删除单条信息不自动删除可能被其他条目或旧版使用的图片。首版不提供单附件删除，避免破坏历史引用；永久删除整个 Agent 时清理其全部附件元数据和 R2 对象。

D1 与 R2 不假设跨存储事务：上传先登记有期限的上传租约，再写 R2 对象和 D1 附件元数据；元数据保存失败时尝试删除新对象，失败对象仍能在按 Agent 前缀清理时发现；请求结束时释放租约，两步成功才回复上传成功。永久删除 Agent 先撤销密钥、停止新写入；有效上传租约尚未排空时保持 `pending`，随后按对象清单分批删除并保留尚未清理的元数据，失败可重试；确认租约、R2 对象和附件元数据均已清空后再删除其他业务记录。开发和测试使用本地 R2 或独立测试桶，不共享生产图片。

# 八、模块组织与工程结构

## 8.1 四个业务模块与认证模块

**Agent 模块**管理 Agent 配置与最近上报。

**条目模块**管理条目、版本、读取、已读、归档和完成状态。版本属于条目内部，不再拆成独立的通用版本服务。

**待办模块**管理简单任务及其来源关联。

**附件模块**负责图片上传、D1 元数据、R2 存取和媒体访问；复用统一身份和 Agent 归属检查。

**认证模块**签发、验证、轮换和撤销 Agent 密钥，并管理网页管理员会话。它只建立可信身份与权限范围，不承载条目业务逻辑。

错误处理和数据库连接属于共用基础设施，不扩展成一套大型业务系统。

## 8.2 一个仓库即可

```text
personal-hub/
├── src/
│   ├── web/
│   │   ├── pages/             页面
│   │   ├── components/        通用界面组件
│   │   └── api.ts             前端请求封装
│   │
│   ├── server/
│   │   ├── index.ts           Worker 导出入口
│   │   ├── app.ts             Hono 中间件与路由装配
│   │   ├── discovery/         分角色 API 使用说明
│   │   ├── modules/
│   │   │   ├── agents/
│   │   │   ├── entries/
│   │   │   ├── tasks/
│   │   │   ├── attachments/
│   │   │   └── auth/
│   │   └── shared/
│   │       ├── authorize.ts   权限范围检查

│   │
│   └── shared/
```

一个业务模块通常分成路由、业务操作和数据库查询几份文件即可。没有必要引入多层抽象类、依赖注入容器或插件注册系统。

依赖关系固定为：

**请求入口 → 模块业务操作 → 数据库查询。**

路由不直接拼 SQL，前端不直接访问 D1，未来 MCP 也只能调用现有业务操作。这样扩展入口时不必重写核心逻辑。

## 8.3 数据库约束

保留基础约束与索引：

**条目必须属于有效 Agent；版本必须属于有效条目；同一条目的版本号不能重复；关联待办不能错误关联到别的 Agent 的条目；主报告和引用图片必须属于对应 Agent；首版只能有一个启用的总管 Agent。** 操作者编号由已验证身份写入，管理员编辑标记为 `manual`；保留操作者历史标识而不级联删除其他 Agent 的历史版本。

查询索引主要围绕 `entries(agent_id, id)` 和 `entry_versions(entry_id, version)` 建立。

读取一个 Agent 的当前条目时，使用集合查询取得最新版本，不逐条发起数据库请求。

所有业务操作都显式接收已经验证的 `actor`。普通 Agent 的 `actor.scope=own`，查询条件必须带自身 `agent_id`；总管的 `actor.scope=all` 只在总管业务操作中生效；管理员 Session 用于管理与网页操作。文档与只读媒体入口按第十章允许三类身份。路由名称本身不构成授权。

# 九、鲁棒性保留在几个明确的地方

## 9.1 创建条目不能只成功一半

“创建条目”和“写入版本 1”必须一起成功或一起失败，不能留下没有正文的空条目。

D1 的 `batch()` 支持事务性批量执行，其中语句失败会回滚整个批次，可用于这个写入边界。([Cloudflare Docs][3])

后端必须等数据库提交成功后才回复成功，不把关键写入丢到后台执行。

## 9.2 版本冲突不自动覆盖

版本已变化就返回冲突，并带回当前版本号。不自动合并、不悄悄重试成下一版，由 Agent 重新读取后决定。

## 9.3 写入超时不等于写入失败

创建请求超时后，可能已经成功。调用方应先重新读取自己的条目确认，再决定是否重试。

首版不做额外的请求去重台账，因此**不承诺一次网络重试绝不产生重复条目**。这一点在 API 说明中写清楚，让 Agent 负责核对。

## 9.4 输入和输出有边界

设置标题长度、正文大小和单次响应大小上限；超过限制明确报错，不截断正文后继续保存。

所有输入执行类型校验。错误统一返回状态码、简短原因，版本冲突额外返回当前版本。日志只记录操作、编号和错误，不记录私人正文或凭据。

前端对 Markdown 使用受限渲染，不执行上传内容中的脚本；数据接口不进入公共缓存。

# 十、认证、部署与恢复

## 10.1 所有鉴权由 Worker 完成

项目不使用 Cloudflare Access。Cloudflare 提供 HTTPS、Worker 运行环境、静态资源、D1 和私有 R2；网页管理员登录、Agent 密钥验证、数据和图片权限全部在 Worker 中完成。

外部 Agent 使用独立 Bearer Key：

```http
Authorization: Bearer phk.<key_id>.<random_secret>
```

Worker 根据 `key_id` 取得候选记录，验证随机秘密的 HMAC 摘要，检查密钥是否过期或撤销，再建立可信身份：

```text
普通 Agent：{ type: agent, agent_id: a001, scope: own }
总管 Agent：{ type: agent, agent_id: manager, scope: all }
网页管理员：{ type: admin, session_id: ... }
```

业务接口按角色分开：普通 Agent 使用 `/api/v1/agent/*`，总管使用 `/api/v1/manager/*`，管理员 Session 使用网页与 `/api/v1/admin/*`。`/api`、`/api/docs` 和只读 `/api/v1/media/{id}` 明确允许三种已认证身份，并分别执行文档范围和图片归属检查。鉴权中间件默认拒绝，只有登录页、其必要静态资源和登录接口可匿名访问。

总管密钥泄漏的影响大于普通密钥，因此设置明确的有效期，支持新旧密钥短时间并存轮换，并在管理页显示创建时间、到期时间和最后使用时间。停用总管 Agent 会立即拒绝其全部业务请求；撤销密钥则返回未认证。

网页使用一个保存在 Worker Secret 中的高强度管理员登录密钥完成首版登录。登录成功后签发随机 Session，浏览器只保存 `Secure`、`HttpOnly`、`SameSite=Strict` 的 `__Host-ph_session` Cookie，D1 只保存 Session 摘要。管理员密钥不进入 D1、前端代码或 `localStorage`。写操作同时检查同源 `Origin`；登录接口按来源限制全部登录请求，成功和失败都会消费限流额度。

新增 Agent 时同时签发第一把密钥并只显示一次。轮换时先签发新密钥，外部执行器切换后再撤销旧密钥；停用普通 Agent 后仅允许它读取自身说明以确认停用，其余业务读写拒绝；停用总管后拒绝全部业务请求。移除 Agent 时撤销其全部密钥，恢复时进入停用状态，需要新密钥并重新启用。总管不能通过自己的 API 签发任何密钥。

## 10.2 发布流程

使用本地开发环境和独立的线上测试环境验证，生产 D1 不与测试共用。

发布顺序固定为：

**测试 → 构建 → 测试环境验证 → 数据库迁移 → 生产部署 → 检查基本读写。**

数据库结构变更存为迁移文件，跟代码一起管理。D1 已有迁移管理能力，不需要自建迁移系统。([Cloudflare Docs][6])

初始部署创建 Worker、D1 和私有 R2 桶，配置数据库及桶绑定。验收普通 Agent 上传图片、管理员网页显示和其他 Agent 越权读取被拒绝的完整流程。

## 10.3 备份与恢复

首版使用 D1 自带的时间点恢复，并保留定期导出和重大迁移前导出的操作说明。D1 免费计划目前提供 7 天时间点恢复，单库上限为 500 MB；历史版本也计入数据库容量。([Cloudflare Docs][7])

D1 支持通过 Wrangler 导出数据库，再将导出内容导入数据库。上线验收时实际做一次恢复到测试库的演练，不只检查“导出文件存在”。([Cloudflare Docs][8])

首版不额外开发备份服务、自动清理历史或数据库归档系统。版本先完整保留，容量需要管理时再增加明确的管理操作。

R2 文件不属于 D1 导出范围。备份说明同时包含数据库导出和 R2 对象复制，保留与元数据一致的对象键；正式备份时暂停写入并等待在途请求结束。恢复演练同时恢复元数据和图片，并核对历史版本图片引用，不把数据库恢复成功等同于图片也已恢复。

## 10.4 最重要的验收项目

| 场景            | 应有结果                      |
| ------------- | ------------------------- |
| 创建条目时第二步写入失败  | 不留下空条目                    |
| 连续追加三个版本      | 当前只展示第三版，前两版仍可读取          |
| 基于旧版本提交更新     | 返回冲突，不覆盖当前内容              |
| Agent 读取自己的条目 | 包含当前完整正文和归档条目，不混入其他 Agent |
| 手动将动态标为已完成或恢复 | 只改变条目完成状态及时间，正文版本、归档、待办保持原状 |
| Agent 默认读取与分页 | 能读到已完成条目、完整正文及完成状态，不能默认过滤掉 |
| 已完成条目追加版本 | 保持已完成；未读新版本显示“已完成 · 有更新” |
| 切换 Agent 展示方式 | 清单与报告无日期分组、不强制左右分栏，内容和状态保持原状 |
| 已认证用户浏览图片或旧版 | 图片正常显示；未认证及其他普通 Agent 无法读取 |
| R2 上传或 D1 元数据写入失败 | 不回复成功；清理或记录孤立对象，允许重试 |
| 普通 Agent 请求总管接口或其他 Agent 条目 | 返回禁止访问，不泄露目标是否存在 |
| 总管跨 Agent 读取和追加版本 | 操作成功，条目归属不变，版本操作者记录为总管 |
| 总管请求密钥、Agent 删除或管理员接口 | 返回禁止访问 |
| 停用或撤销某一 Agent 密钥 | 只影响对应 Agent，不影响其他 Agent |
| 条目超过一页        | 能通过游标读完，无静默截断             |
| 更新已读条目        | 显示有新版本，归档和待办状态不被重置        |
| 主动创建两条相同内容    | 平台按两次创建处理，不执行内容去重         |
| 导出并恢复         | Agent、条目、版本与待办关联保持正确      |

# 十一、首版范围与扩展位置

**首版交付**：普通 Agent 独立密钥、同时至多一个启用的总管 Agent、网页管理员会话、Agent 管理及三种展示布局、条目创建与版本、跨 Agent 管理、完整分页、已读与归档、手动完成和恢复、已完成记录读取、私有 R2 图片上传与展示、简单待办、最近上报、API 说明，以及数据库和图片的部署与恢复能力。

扩展时只在对应位置增加功能：

| 后续需求          | 增加位置             |
| ------------- | ---------------- |
| PDF 等其他附件类型 | 扩展已有附件模块及类型校验 |
| MCP 调用        | 新增入口适配器，复用现有业务操作 |
| 更丰富的运行历史      | Agent 模块增加运行记录   |
| 提醒或推送         | 独立通知模块           |
| 更复杂的待办        | 只扩展待办模块          |

这些功能没有实际需要时，不先建立空模块或预留大量字段。

**最终，平台维护四件核心事实：信息属于哪个 Agent、一个条目有哪些版本、哪一个 Agent 实际提交了版本、你如何处理这些信息。至于内容是否重复、是否有变化、该新建还是追加，都由外部普通 Agent 或总管 Agent 决定。**
